Deviations from the spec

  • Randomize never repeats the previous pick, so from the second click on it draws from the other 18 works. The spec says "from all 19, whatever is typed"; the build reads that as "not limited by the search field" (tracked as T1).

Elevated decisions

The plan kept WINDOWS and ICONS in WindowsProvider, but the provider now imports data/groups.ts, which reads WINDOWS at load: an import cycle that throws.

Options: move them to their own module, or compute folder names lazily in the provider.

Chose: moved verbatim to data/windows.ts, re-exported from WindowsProvider, so every existing import still works.

Reverse: move them back and make groups.ts read WINDOWS lazily.

The spec asks for icons as close to Win95's as possible; tracing Microsoft's bitmaps pixel for pixel would copy their art.

Options: trace the Win9x bitmaps, or draw original pixel art with the same read.

Chose: original 16×16 art in the Win95 style: a flat yellow closed folder; the same folder with a hammer and screwdriver for Control Panel; a dog-eared page under a magnifier for Find.

Reverse: redraw in public/svg/, or trace if you accept that.

Review fix F4: at the planned spot (160, 80), with Randomize at the right of its row, the work Randomize opened covered the button, so the next real click opened nothing. All 19 works open at x ≥ 60, so no spot keeps a right-side button clear.

Options: move Find to x 0 and put Randomize first in its row; or leave it, and you bring Find forward before each click.

Chose: Find opens at (0, 80), its row reads [Randomize] Named: [field]. Trade-offs: after an ITB pick only the button's left part takes clicks (T2); when open, Find covers the desktop icon column below y≈80.

Reverse: set initPos back to { x: 160, y: 80 }, move the button back after the field, drop the F4 test.
